## Historical prerequisite note (resolved through native mode except Docker)

Native local execution: **BLOCKED**. Wrangler/workerd, PostgreSQL server/client,
Docker and Supabase CLI are unavailable on PATH. No existing service or cloud
credentials were accessed. No tools or dependencies were installed.

`capabilities.json` is generated by `node spikes/shared/probe.mjs`. The shared
policy/SQLite reference is not PostgreSQL, Supabase Auth, JWT verification, RLS,
PostgREST/RPC or a database connection-pool test.

To unblock a future local-only experiment, authorize an isolated PostgreSQL
runtime and client/driver in this spike, plus a Workers test runtime. Use a new
disposable local cluster/container and synthetic roles. A full local Supabase
stack additionally needs its supported CLI/container runtime; plain PostgreSQL
can test SQL but cannot validate Supabase Auth. Keep authentication explicitly
mocked for phase 1.

Implement the same quota and upload expectations with real PostgreSQL
transactions, conditional updates and unique constraints. Exercise actual
connection/transaction boundaries and retry/conflict behavior. Separately decide
and test whether access passes through Worker queries, RPC, RLS, or a combination;
an elevated service credential can bypass RLS, so it is not a substitute for a
tested resource authorization boundary. Do not connect to any existing user DB.

Real Google/Supabase JWT issuer/audience/signature/expiry verification, refresh
and revocation require separate identity tests. Remote Supabase and Cloudflare
R2/Images sandbox verification needs express approval and owner-managed sandbox
configuration, never credentials in Markdown or chat. There is no candidate
ranking or recommendation to choose Supabase from the shared pass.
